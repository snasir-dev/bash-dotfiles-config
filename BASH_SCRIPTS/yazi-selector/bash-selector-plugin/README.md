# bash-selector-plugin/

`main.lua` in this folder is a **Yazi plugin** — the actual Lua file Yazi's plugin system loads
and runs, not a snippet or an example. It's the part of `xy` (`x-script-selector-YAZI.sh`) that
runs *inside* Yazi: it binds `l`/`<Enter>`, opens the execute/args/VS-Code (or, in Command
History, execute/edit/cd/open-log) action menu on whatever you're hovering, and writes the
result back out for the bash side to run.

## Why it lives here, not in a "Yazi config" repo

This isn't a standalone, general-purpose Yazi plugin you could `ya pkg add` on another machine.
It only works alongside the rest of `BASH_SCRIPTS/yazi-selector/`: it reads
`$BASH_SELECTOR_CACHE/index.lua` and `history.lua`, both generated by this folder's
`build-index.sh`/`build-history.sh`, and it's driven entirely by env vars
(`BASH_SELECTOR_CACHE`, `BASH_SELECTOR_OUT`, ...) that only `x-script-selector-YAZI.sh` sets.
Without those siblings it does nothing useful, so it's versioned right next to them instead of
off in a separate "dotfiles" repo.

## Why it's symlinked into `~/.config/yazi`

Yazi itself hardcodes where it looks for plugins: `~/.config/yazi/plugins/<name>.yazi/main.lua`.
That path can't be redirected, so *something* has to physically exist there — but on this
machine `~/.config/yazi` is itself a symlink into a separate general-purpose dotfiles repo
(`@SHARED_RESOURCES_REPO`), which manages `~/.config/*` for a whole set of unrelated tools.

The fix is the same trick that repo already uses for this entire repo (see its
`@create-symlinks.ps1`, the `'BASH'` entry in `$Links`): `~/.config/yazi/plugins/bash-selector.yazi`
is a real symlink pointing straight back at *this* folder, created by that same script's
`'yazi/bash-selector-plugin'` entry, run once per machine. `~/.config/yazi/bash-selector-ui.lua`
(the sibling hover-description/linemode file, `../init-snippet.lua` one level up) gets the
identical treatment via a second entry there.

## Why this matters: there used to be two files, not one

Before this was a symlink, `x-script-selector-YAZI.sh` deployed this file with a plain `cp` on
every `xy` invocation (mtime-checked, so it only re-copied when the source had changed). That
meant the file here and the "installed" one in `@SHARED_RESOURCES_REPO` were two **independently
tracked** files that merely happened to have matching content — and editing this plugin required
a *second*, separate commit in that other repo to check in the regenerated copy every single
time. Easy to forget, and a real drift risk if `xy` was ever run (updating the copy) without a
follow-up commit there.

A symlink removes the duplication at the root: there is now exactly one real file on disk,
simply referenced from two repos' working trees. Nothing to keep in sync, nothing to
double-commit, and no way for the two to silently diverge.
